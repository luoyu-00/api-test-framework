# 接口自动化测试框架

基于 pytest + requests + allure 的接口自动化测试框架，覆盖登录鉴权、用户管理、角色管理三个模块共 63 条用例。token 自动注入、YAML 数据驱动、失败重试、敏感字段脱敏与报告发布均已接入，push 触发 GitHub Actions 全量回归。

## 1. 概况

| 项目 | 内容 |
|---|---|
| 被测对象 | 若依（RuoYi）后台接口。本地与 CI 运行在契约模拟器上，见第 2 节 |
| 用例规模 | 63 条：登录鉴权 19、角色管理 20、用户管理 24 |
| 框架分层 | 配置层 / 接口层 / 用例层 |
| 技术栈 | Python 3.11、pytest 8、requests、PyYAML、FastAPI（模拟器）、allure |
| 报告 | 本地 allure 报告；CI 运行后发布至 `gh-pages` |
| 执行耗时 | 全量 63 条约 1 秒（契约模拟器） |
| 持续集成 | GitHub Actions，push / PR / 手动触发 |

## 2. 被测对象与环境分层

```
本地验证 ──→ 真实若依（8080）        业务真实，需 MySQL + Redis
CI 流水线 ─→ sut/ 契约模拟器（8000）   秒级启动，无外部依赖
                  ↑
        同一套用例、同一套断言，只切换 config.yaml 里的 base_url
```

真实若依每次拉起要初始化 MySQL、Redis 与 Java 进程，流水线耗时 3～5 分钟，且环境抖动会与用例失败混在一起。契约模拟器（`sut/`，FastAPI 实现）把被测接口的请求响应契约固定下来，使流水线只反映测试代码本身的状态：用例红了就是用例或框架的问题，不是环境问题。业务正确性的验证放在真实系统上进行。

`sut/` 属于被测对象，与 `testcases/` 严格分离，不为让用例通过而修改其行为。

## 3. 目录结构

```
api-test-framework/
├─ config.yaml              # 环境配置（base_url / 账号 / 超时），用例内零硬编码
├─ conftest.py              # 全局 fixture：配置、token、已登录 client、匿名 client
├─ pytest.ini               # marker 定义与 allure 参数
├─ common/
│  ├─ logger.py             # 双通道日志（控制台 + logs/run.log）
│  ├─ http_client.py        # requests 封装：鉴权注入、重试、耗时统计、脱敏、allure 附件
│  ├─ assert_util.py        # 断言封装，失败信息带响应上下文
│  └─ data_loader.py        # YAML 数据加载
├─ api/                     # 接口层
│  ├─ base_api.py
│  └─ user_api.py           # LoginApi / UserApi
├─ testcases/               # 用例层，只写业务逻辑
│  ├─ conftest.py
│  ├─ test_login.py         # 19 条
│  ├─ test_role.py          # 20 条
│  └─ test_user.py          # 24 条
├─ data/login_data.yaml     # 参数化数据
├─ sut/main.py              # 被测服务（契约模拟器）
└─ .github/workflows/api-test.yml
```

## 4. 运行

```bash
# 起被测服务（另开一个终端，保持运行）
uvicorn sut.main:app --host 127.0.0.1 --port 8000

# 全量执行
pytest

# 只跑冒烟集
pytest -m smoke

# 只跑某个模块
pytest -m role

# 指定环境（config.yaml 中已定义 local / ci）
pytest --env ci

# 生成并查看 allure 报告
allure serve allure-results
```

依赖安装：`pip install -r requirements.txt`。

## 5. 用例覆盖

| 模块 | 用例数 | 其中边界值 | 其中冒烟 | 覆盖内容 |
|---|---|---|---|---|
| 登录与会话 | 19 | 3 | 2 | 正确与错误凭据、空值、超长、验证码、token 与鉴权头、登出后失效 |
| 用户管理 | 24 | 5 | 3 | 列表查询、分页、条件筛选、新增、编辑、删除、重复用户名、状态与长度边界 |
| 角色管理 | 20 | 3 | 1 | 列表与分页、新增、编辑、删除、角色名重复、关键字为空的越权场景 |
| **合计** | **63** | **11** | **6** | |

用例按四类设计：正例（合法参数下业务成功且可查）、反例（必填缺失、类型错误、重复、超长）、边界值（长度与分页取 0 / 1 / 上限 / 上限 +1）、鉴权（无 token、伪造 token、低权限访问）。

## 6. 关键设计决定

| 决定 | 理由 |
|---|---|
| 配置、接口、用例三层分离 | 被测接口改字段时只改 `api/`，用例层不动，降低维护成本 |
| session 级 token，全量只登录一次 | 登录是用例前置条件而非测试目标。63 条各登录一次会产生 63 次无关鉴权请求，既慢又会污染会话类断言 |
| 用例自造数、自清理 | 数据名带时间戳前缀，fixture 用 `yield` 挂清理。重复执行不产生脏数据，第二次跑不会因「用户名已存在」而红 |
| 只对 5xx 与连接异常重试 | 5xx 可能是服务端瞬时故障；4xx 是请求本身错了，重试结果不变，只会拉长执行时间。断言失败不重试，否则偶发通过会掩盖真实缺陷 |
| 断言只比对关心的字段 | 全字段比对会因接口多返回 `createTime` 一类字段而误报。响应全文写入 allure 附件，失败时无需重跑即可定位 |
| 敏感字段落盘前脱敏 | 日志与报告中的 token、密码统一替换为掩码，避免测试产物泄露凭据 |

## 8. 已知限制

- 覆盖范围为登录、角色、用户三个模块，部门、菜单、字典、操作日志尚未纳入。
- 业务断言以 `code` / `msg` 与关键字段为主，未引入 JSON Schema 做结构校验。
- 未做并发与性能验证，框架本身也不具备分布式执行能力。
- YAML 数据驱动目前仅用于登录模块，角色与用户模块仍以代码内参数化为主。
- 契约模拟器与真实若依之间可能存在响应字段差异，切换环境后需重新核对断言。
